# Memory 版本、差异与恢复

工作台提供统一字段差异对比、长期事实回滚和项目 Memory 整体快照恢复。所有操作在本地完成，不调用模型。升级后重启服务并刷新页面；使用原来的 `CASEFORGE_DATA_DIR` 才能看到原项目。

## 页面使用

### 项目快照与整体恢复

1. 选择项目，点击顶部 **Memory 版本**。
2. 填写快照说明，点击 **保存当前项目快照**。建议在调整需求、事实或用例前保存一个基线。
3. 类型选择 **项目整体快照**，选择旧快照，新版本选择 **当前状态**，点击 **对比差异**。
4. 核对后点击 **恢复到所选旧版本**。恢复成功会显示“恢复前自动备份”的 ID。
5. 重新确认模块，再进行评审。需要撤销这次恢复时，选择刚生成的自动备份，与当前状态重新对比后恢复。

每次恢复都会先备份当前项目 Memory，备份与恢复在同一事务中提交。比较之后项目发生变化时返回冲突，需重新对比；正在运行的 Agent 和同项目写操作会阻止恢复。遗留 `running` 状态也会阻止恢复，需要先核实并处理运行状态，不能把正在执行的请求当成已停止。

**模块与决策记忆**、**用例与决策记忆** 共用这个对比入口，可以比较两个已有版本或版本与当前状态。单项恢复仍使用原模块/用例工作区的版本历史按钮；统一弹窗的恢复按钮用于项目快照和长期事实。

旧项目不会凭空产生过去的完整快照。已有模块/用例版本与事实链可以直接对比；整体恢复需要先保存完整快照。

### 长期事实回滚

打开 **知识与记忆 → Adaptive Memory → 版本对比 / 回滚**，选择旧版本与当前活动版本，先对比，再点击恢复。勾选 **显示历史及停用事实** 可以找到历史链。

例如事实从“最多领取 1 张”改成“最多领取 2 张”，回滚会创建第三个版本，内容为“最多领取 1 张”，并用 `supersedes` 关联当前版本。原有两个版本继续保留，检索只使用当前有效事实。回滚记录包含目标版本、原因及原作用域。

仅允许恢复同一事实链上的祖先版本。项目、用户、Agent 等作用域必须一致，当前版本变化后旧请求会被拒绝。已过业务有效期的事实不能通过回滚自动续期；旧版本若没有保存原有效期，也不会猜测它仍然有效，需要显式修订。新增修订会保存被替换记录的原有效期，避免把版本替换时间误当成业务到期时间。

## 整体恢复范围

| 数据 | 恢复行为 |
| --- | --- |
| 需求、解析后的物料、分析、模块、用例 | 恢复所选快照的内容 |
| 模块/用例会话、摘要与结构化决策记忆 | 随项目内容恢复 |
| 模块/用例历史版本 | 合并保留现有历史，再追加恢复版本 |
| 项目长期事实 | 恢复快照状态；快照之后新增的事实保留为 inactive |
| 项目所属知识、采纳示例 | 恢复并按最新人工反馈重新协调；后续新增条目保留为 inactive |
| 项目 badcase | 恢复该项目快照，其他项目记录保留；恢复前内容在自动备份中 |
| 人工反馈 | 保留最新反馈，按恢复后的正文核验；不会用旧快照覆盖后续拒绝 |
| 模块确认、评审、离线评测 | 清空旧确认与评审/评测结果；确认类事实停用，要求重新确认和评审 |
| Supervisor 运行记录、Trace | 保留历史；`memory_epoch` 更新使旧评审凭证失效 |
| 全局事实、团队规则、共享场景规则/模板、其他项目 | 保持现状，不属于单项目恢复范围 |

“项目整体”指具有项目归属的数据集合。团队规则/模板可能影响多个项目，目前缺少完整项目归属，不能随单项目一起回退。上传文件原件、模型配置、密钥和代码文件也不属于 Memory 快照；解析后的物料随项目 JSON 保存。人工验收仍代表用例设计验收，不代表实际接口执行成功。

## 差异与一致性

- 差异统一返回 `changes` 和新增/删除/修改数量，提供路径、前值、后值。具有唯一 ID 的模块、用例、事实列表按 ID 对齐，单纯重排不产生内容差异；步骤等有序列表按内容比较。
- 忽略事实记录的访问统计和更新时间、项目派生验收摘要及更新时间；用例 `test_data` 中同名业务字段仍参与对比和并发校验。
- 快照保存 `schema_version=1`、校验和、项目 ID。恢复前验证完整性、项目范围、重复 ID 和当前用例的模块引用，失败时不写入恢复结果。
- JSON 是数据源；向量索引是派生缓存，不做跨 JSON/SQLite 的事务恢复。检索按活动 JSON 条目及内容指纹选择缓存向量，人工示例还需核验源项目最新正文与反馈。

## 原子恢复的实现与边界

同一数据目录在单个服务进程内共用锁。恢复在锁内校验、生成备份并写入撤销日志 `.memory-transaction.json`，随后替换项目、事实、知识、badcase、备份及恢复回执文件；删除撤销日志为提交点。

写入发生异常时，按日志恢复所有文件原始字节，并移除本事务新增的文件。进程在提交点之前中断时，下次打开 `JsonStore` 或读取/写入 JSON 前先恢复旧状态。恢复失败时日志保留并报错，不把部分写入当作成功。应用通过存储接口读取时会等待正在执行的恢复事务；需要跨多次读取保持同一视图的调用应使用 `memory_transaction()`。

此保证适用于当前**单进程服务**。不要用多个 Uvicorn worker 或外部脚本同时写同一数据目录。直接读取磁盘的外部程序不受锁保护；硬件断电、文件系统损坏和分布式事务不在本轮保证范围内。Memory 文件事务恢复不等于模型调用或 Agent 动作重放。

本地文件位于 `CASEFORGE_DATA_DIR`：

```text
memory_snapshots/<project_id>/MS-<id>.json  # 不可变快照、恢复前备份
memory_restores/<project_id>/MR-<id>.json   # 恢复回执与备份关联
.memory-transaction.json                  # 事务期间的撤销日志
```

沿用运行数据忽略规则，不上传这些包含项目内容的文件。

## API

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/projects/{id}/memory-versions` | 完整快照及模块/用例版本目录 |
| `POST /api/projects/{id}/memory-versions` | 创建快照，正文 `{"label":"变更前"}` |
| `POST /api/projects/{id}/memory-versions/diff` | `kind` 为 `snapshot/cases/modules`，传 `left_id`、`right_id`（默认 `current`） |
| `POST /api/projects/{id}/memory-versions/restore` | 传 `snapshot_id` 及上次差异响应中的 `expected_fingerprint`（值取 `current_fingerprint`） |
| `GET /api/memory/{id}/history` | 同一事实版本链与 `current_id` |
| `GET /api/memory/{id}/diff?target_id={old_id}` | 两个事实版本的差异 |
| `POST /api/memory/{id}/rollback` | 传 `target_id`、`expected_current_id`、可选 `reason` |

恢复响应包含 `backup_id`、恢复回执 ID 和最新 `project`。版本冲突、过期事实、运行中项目等返回 409；客户端需要显示原因，不能自行绕过校验反复提交。
